## 3. 识别准确性问题（有真实样本）

### 3.1 同类邮件分类不一致（智联推荐营销邮件 11 封）

|---|---|---|---|

| #21 | 杭州银行 2027 届秋季校园招聘 | career_talk | item15（厦大宣讲会 9-18 14:30） |
| #22 | 中国太平 暨南大学专场宣讲会 | career_talk | item16（暨大专场宣讲会 9-21 19:00，**在广州**） |
| #18 | 波克 2027 秋招空中宣讲会 | career_talk | item12（直播 9-16 19:00） |
| #30 | 【诚邀您投递】杭州银行…火热进行中！ | notification | 不建项 |

→ 相同性质的营销/推荐邮件，一半进待办一半不进，规则不可预期。

### 3.2 时间理解错误（±8 小时）

- **item5（曦望笔试）**：正文「请务必在收到邮件作答通知后，**72 小时内**完成作答」，发件时间 `2026-09-07T10:29:27+00:00`（= 北京时间 18:29）。
  Agent 给出 `2026-09-10T10:29:27+08:00`（= 09-10 02:29 UTC）——**比真实截止早 8 小时**。
  根因：Agent 提示词里的「发件时间」用的是库里的 UTC 串，模型直接照抄墙钟时间再补 `+08:00`；
  而管线自带的确定性推算（`infer_relative_deadline`）算的是正确时刻（同批 #14/#15 国开行测评 = 发件+72h UTC，正确）。
  即：**同一个语义，Agent 路径和管线路径给出两个不同时刻**。
- **item14（蔚来预约面试）**：正文「链接将于 **24 小时后失效**，请尽快操作」→ 未识别，`deadline=NULL`。
  现有正则只认「N 小时内/日内 + 完成/回复/确认…」这类“动作+时限”，不认「N 小时后失效/过期」。
- **item3（米哈游面试直通车）**：正文列了 6 个场次（9/15 上海 … 11/2 杭州），无单一截止 → 未建 deadline（合理），
  但也没有把「最近一场 9/15」作为可行动时间。

### 3.3 分类 id / label 混用

- **item18**（邮件 #24，上饶银行宣讲会）的 `items.category = 宣讲会`（中文 label），而其它同类事项是 `career_talk`（id）。
  根因：Agent 这一封返回 `item=null`，管线走旧 `extract_todo` 路径，提示词允许返回「可选二级类型 category」，
  模型填了「宣讲会」，管线**未校验是否为合法分类 id** 就直接落库。
- **提醒主题会退化**：`notifier` 的 `【类型/…】` 取自 `llm.yaml` 静态分类表（`cfg.category_label`），
  运行期新建的 `career_talk` 不在其中 → 主题会变成 `【career_talk/上饶银行/上饶银行宣讲会/0918】`（英文 id 泄漏）。

## 4. 待办「安排」不合理

1. **营销邮件淹没待办**：21 条待办里 **9 条**是智联推荐群发（宣讲会/双选会/网申截止），
   真正与求职行动相关的只有面试 5、笔试 3、测评 3、简历更新 1。
2. **同一家公司多条待办不合并**：蔚来 3 条（item7 测评 / item14 预约面试 / item20 面试）、
   国家开发银行 2 条（重复）、上饶银行 2 条（重复）。
3. **提醒策略单一**：全部按「截止前 1 天 09:00」。对「24H 内完成」的紧急事项（如 Shopee 简历更新 09-09 10:23 截止）只在 09-08 09:00 提醒一次；
   对「24 小时后失效」的预约链接（item14）根本不提醒；对宣讲会（9-16 19:00）在前一天 09:00 提醒，时效性一般。
4. **事件名被硬截断**：item4 `event=推理引擎研发工程师面`（`clamp_event` 取前 10 字，截在词中间）。
5. **历史/过期事项不清扫**：item2（京东笔试 09-05 19:00）在本机当前时间看已过期，会立刻转 `expired`，
   但用户并没有得到「这条已经不用做了」之外的信息；老库中同类堆积会越来越多。
6. **待办无优先级/无分组**：所有事项平铺，不区分「必须我行动」「可以参加」「仅供参考」，
   也不区分紧急度，11 条未过期待办里 9 条在未来 3 天内集中到期（9-08 ~ 9-21）。

## 5. 工程/环境问题（本次跑批暴露）

1. **本机时钟与邮件时间不一致**：本机 `2026-09-06 18:32 UTC`（= 09-07 02:32 +08），
   但 INBOX 最新邮件日期是 `2026-09-17`，**邮件比本机“未来”约 11 天**。
   这会直接影响：过期清扫（`deadline < now → expired`）、提醒触发时刻、相对时限推算基准。跑正式提醒前必须先校准时钟。
2. **首次拉取是全量**：`fetch-once` 在游标为空时 `UID FETCH 1:*`（本次 240 封全量下载，约 30–60s），
   只有 `--limit`（按 UID 取尾部）可用，没有「只处理最近 N 天」的选项；真实邮箱邮件多时首跑成本高。
3. **提醒链路未验证**：本次全程 `--no-check`（零发送），`send_log`/SMTP/回复识别（【已完成】/【不再提醒】）尚未在真实邮箱上跑通。
4. **日志无 token 统计**：`LLM 调用完成` 只记 content 长度与耗时，无法直接从日志核算成本。

## 8. 已确认需求（用户选择）

1. **待办口径**：只保留需要本人亲自行动且有时间的（面试/笔试/测评/预约/材料提交）；
   宣讲会/双选会/网申推荐/投递邀请只做通知。
2. **分类体系**：允许 Agent 新建分类，但必须落库校验 id/label 且**默认不自动建项**。
3. **提醒策略**：分级提醒 —— 24h 内紧急：收到即提醒 + 截止前 2h；中长期：T-1 09:00；链接失效类：立即提醒。
4. **合并去重**：同一件事合并为一条，以最新邮件为准（同公司同类型覆盖更新）。
5. **下一步**：先按需求改规则/提示词，再清库重跑做前后对比；同时跑完全量 240 封看整体分布。

## 11. 遗留与建议

1. **本机时钟**：本机 2026-09-06（UTC）/ 09-07 02:xx（+08），而 INBOX 最新邮件为 2026-09-17 →
   过期清扫与提醒触发都会受“邮件在未来”影响。正式启用提醒前请先校准系统时钟。

   （见 §13，发送成功）；失败重试与回复「已完成/不再提醒」仍只有 e2e（greenmail）覆盖。
   注意：`serve` 与 `check-once` 都会对到期的待办真实发信。

# 第四部分：修复「自动拉取会把邮件标成已读」（需求 3）

## 14. 根因与修复

- **根因**：`src/mail/imap.rs` 收信使用 `UID FETCH (RFC822)`。按 RFC 3501，`RFC822` 等价于 `BODY[]`，
  **会隐式设置 `\Seen`**，于是每轮轮询都把用户邮箱里没读过的邮件标成已读。
- **修复**：改为 `UID FETCH (BODY.PEEK[])`（只读取内容，不改任何标志位）；
  测试辅助函数 `read_inbox` 也同步改为 `BODY.PEEK[]`，避免测试自身改动标志位。
- **验证**：新增 e2e `e2e_fetch_does_not_mark_mail_as_seen`
  （投递 1 封 → 断言未读 1 封 → 跑完整流水线 → 仍未读且邮件正常入库）。
  把代码临时改回 `RFC822` 时该用例会失败（已实测），说明回归被锁住。
  全量 **53 单测 + 28 e2e 全绿**。
- **程序不会改动邮箱的任何状态**：不设置/清除 `\Seen`、`\Flagged`，不删除、不移动、不建文件夹。

## 15. 存量影响

- 在修复前跑过的几轮拉取（240 封）已经把那批邮件在服务器上标成了已读，**原始已读/未读状态无法还原**
  （IMAP 不提供历史状态）。如需重新过一遍，可在邮箱客户端里把这批邮件手动标记为未读，
  或后续按需增加一个「按 UID/日期范围批量标记未读」的运维命令。
